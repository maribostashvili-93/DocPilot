# DocPilot UX System Audit - Issue To Fix Table

Date: 2026-05-23
Phase: 1 - UX system audit

This table converts the Phase 1 audit into PM-discovery input. No backlog ticket IDs are assigned here; ticket creation belongs to Phase 3 after discovery.

| Finding ID | Source items | Problem | User impact | Severity | Recommended fix | Candidate milestone | Success signal |
| --- | --- | --- | --- | --- | --- | --- | --- |
| UX-01 | A-24, A-40, A-42, P-12, P-22 | Publish actions are immediate metadata changes, not governed release operations. | Users can believe content is truly published or snapshotted when no immutable release exists. | P0 | Implement staged publish workflow with immutable snapshots, actor, approval, environment, timestamp, and rollback. | M1/M3 | Publish creates an auditable snapshot and cannot bypass readiness/approval gates. |
| UX-02 | A-45, P-09 | Core CMS data persists only in browser storage. | Production content can be lost, cannot sync, and cannot be audited. | P0 | Move products, docs, sections, translations, releases, users, revisions, and media metadata to backend persistence. | M1 | Data survives browser/device changes and every mutation has server-side audit metadata. |
| UX-03 | A-43, A-44, E-37, P-18 | Auth and roles are local prototype constructs with only partial route gating. | Enterprise governance cannot be trusted. | P0 | Add real authentication and action-level RBAC for admin, editor, reviewer, viewer, partner/TAM/developer roles. | M1/M3 | Unauthorized users cannot perform restricted read/write/publish/user actions. |
| UX-04 | A-22, E-18, P-08 | Revision history is local/session-scoped and not tied to publish snapshots. | Users overestimate recovery and audit guarantees. | P0 | Implement durable revision history with diff, actor, restore, rollback, and release linkage. | M1/M2 | A user can restore any persisted revision and trace it to a release or draft state. |
| UX-05 | A-08, A-14, A-36, E-07, P-14 | Product, document, and translation scope labels are inconsistent. | Editors can work in the wrong scope or misunderstand what is being edited. | P1 | Define explicit hierarchy: workspace -> product -> documentation space/document -> section -> locale. Add global scope bar. | M1/M2 | Every admin page shows the same active product/document context and switching warns on dirty edits. |
| UX-06 | A-10, A-17, E-14 | Document and section creation omit IA fields such as slug rules, audience, template, and nav placement. | New docs require manual cleanup and cannot support WordPress-like organization. | P1 | Add document template, slug validation, audience/visibility, taxonomy, and menu placement during creation. | M2 | A new document appears in the intended menu/taxonomy with correct visibility and starter structure. |
| UX-07 | A-18, P-05 | Raw HTML editing is exposed as a normal mode without validation. | Nontechnical editors can break content structure or unsafe links. | P1 | Move HTML to advanced mode with validation, sanitized preview, and diff before save. | M1/M2 | Invalid HTML or unsafe embeds cannot be saved without explicit validation pass. |
| UX-08 | A-20, E-23, P-04 | Inline editing relies on hover and floating edit affordances. | Touch, keyboard, and novice users may not discover or operate core editing. | P1 | Add selected-section inspector/list of editable elements, keyboard focus path, and persistent edit affordance. | M1 | All inline-edit targets can be reached and edited without mouse hover. |
| UX-09 | A-23, A-30, E-20, E-28, P-06 | Drag/reorder/marker manipulation lacks keyboard and precision alternatives. | Accessibility and exact positioning suffer. | P1 | Add keyboard reorder/nudge, grid/snap, coordinate inspector, and clear focus states. | M1 | Sections and markers can be positioned with keyboard and numeric controls. |
| UX-10 | A-28, E-26, E-27 | Media editing depends on raw URLs and no asset library. | Editors need developer-like paths and cannot reuse/tag media. | P1 | Build media library with upload/select/reuse/tagging, alt text enforcement, and usage tracking. | M2 | An editor can insert/reuse a media asset without typing a URL. |
| UX-11 | A-32, E-29, E-30, P-01 | Marker styling controls are too dense and advanced by default. | Screenshot annotation takes excessive time and creates inconsistent styling. | P1 | Use preset-first marker styling with collapsed advanced sections and shared design tokens. | M1 | Default marker creation requires only content, type, position, and preset. |
| UX-12 | A-33 | Marker destinations lack URL/anchor validation. | Broken internal or external links can be saved. | P1 | Validate section anchors and external URLs; warn on broken targets before save/publish. | M1/M2 | Invalid targets are blocked or visibly flagged. |
| UX-13 | A-35 | Full section editor has a duplicate annotated-image path separate from screenshot modal. | Users face two marker editors with different behavior. | P1 | Consolidate annotation creation/editing into one screenshot editor. | M1 | All annotation paths use the same marker model and inspector. |
| UX-14 | A-07, E-04 | Current route map lacks settings/workflow surfaces expected by handoff and objective. | Users cannot configure platform/workflow concepts from UI. | P1 | Add Settings and Workflow/Governance areas or explicitly remove stale references. | M1/M3 | Navigation matches documented product capabilities. |
| UX-15 | A-12, E-10 | Permanent deletes are confirmed but not archived or undoable. | Important content can be lost. | P1 | Add archive/trash for documents/sections/users/media with restore. | M2/M3 | Deleted content can be restored by authorized users. |
| UX-16 | A-38, E-34 | Translation edits autosave silently without dirty/saved state or review comments. | Translators and reviewers lack confidence and collaboration tooling. | P2 | Add per-row dirty/saved state, reviewer comments, and status per string or section. | M3 | Users can see saved state and review status for each translation item. |
| UX-17 | A-37, E-33, P-16 | Translation search/filter is strong but narrow. | 37-language review requires too much scanning. | P2 | Add status/reviewer filters, next-missing navigation, and dashboard deep links. | M3 | Reviewer can complete missing-string triage without manual scanning. |
| UX-18 | A-09, E-06, P-16 | Dashboard attention items are not deep-linked to filtered work. | Users must rediscover the problem after clicking. | P2 | Link dashboard items to exact document/section/language filters. | M2/M3 | Clicking an attention item opens the relevant page with target selected. |
| UX-19 | A-13, A-42 | Preview and publish states are not visually distinguished enough. | Editors may confuse draft preview with published reader state. | P1 | Add preview banners, draft/published/environment labels, and role/audience indicators. | M1/M2 | Reader preview always states source state and intended audience. |
| UX-20 | E-16, E-19, P-21 | Action bars and per-section controllers use many compact icon-only actions. | Discoverability and misclick risk increase. | P2 | Move secondary actions to overflow, use standard icons/tooltips, and support expanded labels. | M1 | Primary actions are obvious; secondary/destructive actions are separated. |
| UX-21 | A-21, E-11 | Inline delete and some reversible changes do not expose immediate undo. | Users may miss how to recover accidental edits. | P2 | Add undo toast and visible recent-change affordance. | M1 | User can undo a recent delete/save from visible feedback. |
| UX-22 | A-41, E-35, E-36, P-11 | Readiness blockers are visible but not actionable. | Users know release is blocked but not where to fix it. | P2 | Link each readiness reason to exact remediation page/filter/field. | M1/M3 | Every blocker has a direct "fix" path. |
| UX-23 | E-08 | Operational tables lack sorting/filtering/bulk controls. | Scale beyond seed data becomes slow. | P2 | Add table controls, saved filters, and bulk actions where safe. | M4 | Users can manage larger user/release/document sets efficiently. |
| UX-24 | A-39 | Adding a language has no owner, due date, or setup options. | Localization launch planning remains manual. | P2 | Add language setup workflow with reviewer, due date, source clone options, and status. | M3 | New locale enters a trackable workflow with ownership and milestones. |
| UX-25 | A-03, E-01 | Branding still mixes Aviator and DocPilot. | Buyers and editors may mistake demo content for product identity. | P2 | Rename visible platform shell to DocPilot and keep Aviator as sample product. | M1/M4 | First viewport and admin shell consistently communicate DocPilot as product. |
| UX-26 | P-20, E-12 | Validation is mostly native or ad hoc. | Data quality problems surface late. | P1 | Add schema validation for docs, sections, slugs, URLs, versions, release labels, and marker fields. | M1/M2 | Invalid data shows inline errors and cannot reach publish. |
| UX-27 | A-26, E-21 | Element insertion supports both click-place and drag but does not explain state. | Users may not know how to place selected components. | P2 | Add insertion mode banner, visible drop zones, and escape/cancel affordance. | M2 | Component insertion is obvious in both click and drag paths. |
| UX-28 | A-31 | Changing marker type mutates layout/defaults silently. | Users can lose careful placement or content choices. | P2 | Show type-change preview and preserve compatible values. | M1 | Type switching is reversible and transparent. |
| UX-29 | P-19 | Accessibility is partial but not systematic. | Keyboard/screen-reader users cannot complete all core flows. | P1 | Add accessibility checklist and acceptance criteria for keyboard, focus, aria, and reduced-motion behavior. | M1-M4 | Every PM backlog item includes accessibility acceptance criteria. |
| UX-30 | A-02, E-38, P-13 | Empty states lack full setup guidance. | Product onboarding is fragmented. | P2 | Add guided setup checklist for product, first doc, audience, locale, media, snapshot. | M2 | New product onboarding can be completed from one guided path. |
